# PyNet: Our Own Event Loop and Real Networking — Design

**Date:** 2026-10-16
**Status:** Draft for approval
**Part of:** the dependency upgrades that come before the job scheduler
(order: **pynet** → pymq → pyweb → pydb → scheduler)

## 1. Intent and why

We are going to build an Autosys/Control-M-style job scheduler as the next
learning module. It is a long-running service where efficient concurrency is
fundamental: it runs many subprocesses at once, talks to remote agents,
watches files, fires timers and pushes live updates to a web dashboard.

None of our existing modules can carry that today. PyNet is mostly
*simulation* (TCP handshake state machine, WebSocket frames as plain data
holders, etc.) — there is no real TCP server/client, no framing, no
persistent connections. pymq and pyweb, which the scheduler also needs, are
synchronous and single-connection.

So PyNet grows a **real, from-scratch concurrency and networking layer**,
built on our **own event loop** (not `asyncio`) — because this is a learning
series and the event loop is exactly the "magic" worth opening up. pymq,
pyweb and the scheduler will all run on this loop.

The existing simulations **stay**, side by side with the real
implementations. Both are useful for learning: the simulation shows the idea
step by step, the real version shows it working on the wire.

## 2. Goals

1. A **reactor** event loop built on `selectors`: wait on many sockets/pipes
   at once, run callbacks when ready, plus a timer heap.
2. A **task layer** that drives ordinary `async def` / `await` coroutines on
   our loop, with futures, cancellation, timeouts and basic sync primitives.
3. Non-blocking **TCP streams** (server and client).
4. **Length-prefixed framing** of messages.
5. A **message protocol** over framed connections: request/response, server
   push, heartbeats and auto-reconnect — the transport for scheduler ⇄ agent
   (and pymq's network broker).
6. **Subprocesses** on the loop: launch a command, read stdout/stderr without
   blocking, detect exit, kill a whole process group.
7. **Thread interop**: run a blocking function in a worker thread and await
   its result; wake the loop safely from another thread.
8. A **real WebSocket** (RFC 6455) implementation on our streams, for pyweb's
   live dashboard.
9. **Kid-friendly docs for every piece** (see §7) — this is a first-class
   deliverable, not an afterthought.
10. PyStack integration kept working and extended (see §8).

## 3. Non-goals

- **TLS / encryption / agent authentication.** Plain connections on a trusted
  network for now; TLS can be added later.
- **Windows support.** macOS (dev) and Linux (CI) only — we rely on
  `SIGCHLD`, `fork`-style subprocess semantics and POSIX process groups.
- **asyncio compatibility.** Our loop does not run asyncio coroutines or
  libraries, and asyncio does not run ours. Mixing them should fail with a
  clear error, not mysteriously hang.
- **Guaranteed delivery.** PyNet is about *connections*. Persistence,
  acknowledgement, redelivery and replay after a reconnect are **pymq's**
  job in the next project.
- **An HTTP server.** That is pyweb's job (next-but-one project). PyNet gives
  pyweb the streams and the WebSocket pieces it will need.
- **Real UDP, SMTP, FTP, DNS servers.** Those simulations stay simulations.
- **Matching asyncio's performance.** Clear beats clever, but see the
  anti-goal on busy-spinning.

## 4. Anti-goals (would be a failure even if it "works")

- **A loop that busy-spins** or polls on a short sleep instead of blocking in
  `select` until something is ready or the next timer is due. Idle must mean
  ~0% CPU.
- **Hidden magic.** If a reader can't follow how `await` reaches the
  selector by reading our code and docs, we failed.
- **Docs that lag the code**, or real modules without their analogy page.
- **Losing the simulations** or breaking existing public APIs (the PyStack
  `net` plugin uses `resolve`, `b64_encode`, `b64_decode`, URL parsing).
- **Silent failures**: an exception in a task, a callback or a dead
  connection must be visible (logged and/or surfaced), never swallowed.

## 5. Constraints

- Python **>= 3.14**, zero runtime dependencies (stdlib only, and not
  `asyncio`).
- Existing PyNet tooling: uv, ruff (broad rule set incl. docstrings and
  PLR2004 named constants), **pyright strict**, pytest with ≥80% coverage,
  commitizen conventional commits, PRs from feature branches (main is
  protected), CI on GitHub Actions.
- **TDD** (red → green → refactor).
- User rule: **never use `TYPE_CHECKING` or `from __future__ import
  annotations`.** New code must not use them. 7 hand-written PyNet files
  currently use `__future__` — remove it from them as part of this work (my
  call; it's a standing rule). `src/pynet/_version.py` is generated by
  hatch-vcs and is out of scope.
- Google-style docstrings, imperative mood, with analogy-flavoured module
  docstrings matching the existing style ("Registered mail -- reliable,
  ordered delivery.").

## 6. The design (layers)

The layering below is Claude's call (the user approved "our own loop",
"keep the simulations", "plain for now"). It intentionally mirrors how
asyncio itself is layered so a comparison doc page is easy to write.

```
 Layer 5  WebSocket (RFC 6455)         ws server/client on streams
 Layer 4  Message protocol             request/response, push, heartbeats, reconnect
 Layer 3  Streams + framing            TCP server/client, length-prefixed frames
 ───────────────────────────────────────────────────────────────────────────
 Layer 2  Tasks                        async/await, Future, Task, cancel, timeout,
                                       sleep, gather, Event, Queue, Lock,
                                       subprocesses, run_in_thread
 Layer 1  Reactor                      selectors + ready queue + timer heap
                                       + self-pipe wakeup
```

### 6.1 Layer 1 — Reactor ("the waiter")

- One loop object owning: a `selectors.DefaultSelector`, a FIFO ready queue
  of callbacks, a min-heap of timers, and a **self-pipe** (socketpair) for
  wakeups.
- One iteration: compute the timeout until the next timer (or block forever
  if nothing is scheduled, `0` if callbacks are ready) → `select(timeout)` →
  queue callbacks for ready fds → move due timers to the ready queue → run
  everything that was ready *at the start* of this iteration (so a callback
  that schedules another doesn't starve I/O).
- API (names are the builder's to finalise, shape is fixed):
  `call_soon(cb)`, `call_later(delay, cb)` / `call_at(when, cb)` returning a
  cancellable handle, `add_reader(fd, cb)` / `remove_reader`, `add_writer` /
  `remove_writer`, `call_soon_threadsafe(cb)` (writes a byte to the
  self-pipe), `run_forever()`, `stop()`, `close()`.
- **Injectable clock**: the loop takes a monotonic time function so tests can
  drive timers deterministically with a fake clock.
- Errors in callbacks are caught, reported through a loop exception handler
  (default: log with traceback), and do not kill the loop.

### 6.2 Layer 2 — Tasks ("bookmarks in a recipe")

- Our own `Future` (result / exception / cancelled + done callbacks). Its
  `__await__` yields itself to whichever Task is driving the coroutine.
- `Task` drives a coroutine by calling `send()`/`throw()`; when the coroutine
  yields a Future, the Task registers a done-callback and steps again when it
  resolves. Yielding anything other than our Future raises a clear error
  (this is how mixing with asyncio is caught).
- **Cancellation**: `task.cancel()` throws a `Cancelled` exception into the
  coroutine at its current `await`; `finally` blocks run. Timeouts are built
  on cancellation: `async with timeout(seconds): ...` raising a `TimeoutError`.
- Helpers: `run(main_coro)` entry point (creates a loop, runs to completion,
  closes it), `sleep(seconds)`, `spawn(coro)` / `create_task`, `gather(...)`,
  `wait_for(coro, timeout)`.
- Sync primitives for coroutines: `Event`, `Queue` (bounded, with
  `put`/`get` that await), `Lock`, `Semaphore` (the scheduler will use this
  for concurrency limits / resource pools).
- Unhandled exceptions in a task that nobody awaits are reported (logged),
  never silently dropped.
- **Subprocesses** (lives at this layer because it needs only the loop, not
  sockets):
  - Launch via `subprocess.Popen` with pipes for stdout/stderr (and stdin),
    `start_new_session=True` so each job gets its own **process group**.
  - Pipes are set non-blocking and registered with the reactor; output is
    readable as async streams (so the scheduler can tee into log files
    without blocking).
  - Exit detection: a `SIGCHLD` handler writes to the self-pipe; the loop
    then reaps tracked children with `waitpid(..., WNOHANG)` and resolves
    each process's exit future. This teaches the classic *self-pipe trick*.
  - **One child watcher per process** (Claude's call). Signal handlers can
    only be installed from the main thread, and there is only one
    `SIGCHLD`, so a single process-wide watcher owns the handler. It keeps
    a table of `pid → owning loop` and hands each exit to that loop via
    `call_soon_threadsafe`. Consequences:
    - The watcher is installed from the main thread (automatically by
      `run()` when it is called there, or explicitly).
    - A loop running in a background thread **can** spawn subprocesses once
      the watcher is installed; if it isn't, spawning raises a clear error
      explaining why (tested).
    - Several loops in one process work (tests need this). A scheduler and
      an agent in the same process are expected to share **one** loop.
    - The watcher reaps only pids it launched (`waitpid(pid, WNOHANG)` per
      tracked pid, never `waitpid(-1)`) so it doesn't steal other code's
      children.
    - kqueue `EVFILT_PROC` / Linux `pidfd` are mentioned in the docs as
      "how the pros do it" but not implemented.
  - `wait()`, `returncode`, `send_signal`, `terminate`, `kill`, and
    **kill-process-group** (needed for job timeouts so grandchildren die too).
- **Threads**: `run_in_thread(fn, *args)` runs a blocking call (e.g. a pydb
  query, a file `stat`) on a small worker-thread pool and returns an
  awaitable; completion is delivered back to the loop via
  `call_soon_threadsafe`.

### 6.3 Layer 3 — Streams and framing ("envelopes with the length written on")

- `start_server(handler, host, port)` → a server object; each accepted
  connection calls `handler(reader, writer)` as a new Task.
- `open_connection(host, port)` → `(reader, writer)`.
- `reader`: `read(n)`, `read_exactly(n)`, `read_until(sep)`, EOF handling.
- `writer`: `write(bytes)` buffers; `await drain()` applies **backpressure**
  (waits until the send buffer drops below a high-water mark); `close()` /
  `await wait_closed()`.
- **Framing**: 4-byte big-endian unsigned length + payload. A configurable
  **maximum frame size** (default e.g. 16 MiB) — oversize frames close the
  connection with a clear error (protects against garbage/hostile input).
  `FramedConnection` with `send_frame(bytes)` / `recv_frame() -> bytes`.

### 6.4 Layer 4 — Message protocol ("walkie-talkies with call signs")

- Messages are **UTF-8 JSON objects** inside frames, with a small envelope:
  `v` (protocol version, starting at `1`, so pymq and the scheduler can rely
  on a stable, evolvable wire contract), `type` (`request` | `response` |
  `error` | `push` | `ping` | `pong`), `id` (for request/response matching),
  `method`, `body`.
- **Binary attachments** (Claude's call): pymq payloads and job output are
  bytes, and base64-in-JSON wastes a third of the space. Each frame's first
  byte is a **kind** marker: `J` = JSON envelope, `B` = raw binary. An
  envelope may declare `"attachments": n`, meaning the next *n* frames on the
  connection are raw binary belonging to it; the API exposes them as
  `message.attachments: list[bytes]`. Each attachment still obeys the max
  frame size.
- **Bulk data** is *not* streamed through one giant message. Large things
  (e.g. a job's log) are fetched in chunks by request (`offset`, `limit`), or
  pushed incrementally as many small messages. Job logs live on the agent's
  machine; the scheduler/UI asks for slices. (The scheduler design will
  pin this down; PyNet just needs the attachment mechanism and frame cap.)
- **Request/response**: `await conn.request(method, body, timeout=...)`;
  the peer registers handlers per method. Many requests can be in flight on
  one connection at once (matched by `id`).
- **Push**: either side can send one-way messages (`conn.push(method, body)`)
  — e.g. agent → scheduler "job 42 exited 0", scheduler → agent "kill job 42".
- **Heartbeats**: ping every *interval*; the connection is declared **dead**
  after *N* missed pongs (both configurable). Death is surfaced as an event /
  callback so the scheduler can mark an agent lost.
- **Reconnect** (client side): exponential backoff with jitter and a cap;
  emits `connected` / `disconnected` / `reconnected` events. **No replay** of
  messages sent while disconnected — sends while down raise a clear
  "not connected" error. (Guaranteed delivery is pymq's job.)
- Malformed JSON or unknown message types produce an `error` reply where
  possible and are logged; they do not crash the connection's peer.

### 6.5 Layer 5 — Real WebSocket ("the phone call, for real")

- Implements RFC 6455 on our streams: opening handshake (computing
  `Sec-WebSocket-Accept` = base64(SHA-1(key + GUID)); SHA-1 from `hashlib`,
  base64 from PyNet's own encoder), frame encode/decode (FIN, opcodes,
  7/16/64-bit lengths), **client masking**, text and binary messages,
  fragmentation (continuation frames), ping/pong, close handshake with
  status codes, and a max message size.
- Server side is the priority (pyweb will hand an upgraded connection to
  it); a minimal client is included so tests and examples can talk to the
  server.
- Lives beside the existing `websocket.py` simulation (which stays as-is);
  the simulation doc links to the real one and vice versa.
- The HTTP *parsing* of the upgrade request belongs to whoever runs the HTTP
  server. PyNet exposes the handshake as functions over a request's headers
  plus a stream, so pyweb can call it.

### 6.6 Module layout (suggested; builder may adjust names)

```
src/pynet/
  (existing simulation + util modules stay where they are)
  loop/            reactor, timers/handles, futures, tasks, sync primitives,
                   timeout/cancellation, threads, run()
  process.py       async subprocesses   (not "subprocess.py" — avoid
                                         shadowing confusion with stdlib)
  streams.py       TCP server/client, reader/writer, backpressure
  framing.py       length-prefixed frames
  messaging.py     message protocol, heartbeats, reconnect
  ws/ or wsreal.py real WebSocket (handshake, frames, connection)
```

## 8. PyStack integration

PyStack already depends on PyNet (path dep) and has a `net` plugin
(`src/pystack/plugins/net_plugin.py`) exposing DNS, URL and Base64 to Pebble
plus a `dns` shell command. That must keep working unchanged.

Extend it in a way that shows the new loop off without dragging async into
Pebble: e.g. a shell command that runs a tiny loop demo (an echo
round-trip on localhost, or "run 3 commands at once and show they overlap")
and prints what happened. Exact command(s) are the builder's call; update
PyStack's tests and README per its usual integration pattern.

**Granularity** (from the user's standing rule: integrate immediately, not
later): every PR that adds a user-visible layer also updates PyStack in the
same step — not one big integration at the end. Roughly: loop + subprocesses
→ "run commands at once" demo; streams/messaging → echo/ping demo;
WebSocket → WebSocket echo demo. Each comes with PyStack tests and README
rows. Internal-only PRs (e.g. the `__future__` cleanup) need no PyStack
change beyond keeping its CI green.

## 9. Testing approach

- TDD throughout. Real sockets on `127.0.0.1` with ephemeral ports for
  stream/messaging/WebSocket tests; real short-lived subprocesses (`echo`,
  `sleep`, `sh -c "exit 3"`) for process tests.
- Fake clock for timer, timeout, heartbeat and backoff tests so they are
  fast and deterministic.
- Every test runs under a hard per-test timeout so a loop bug fails fast
  instead of hanging CI.
- Explicit tests for the anti-goals: idle loop blocks in `select` (no
  spinning), exceptions in tasks/callbacks are reported, unawaited task
  failures are logged.
- ≥80% coverage; pyright strict and ruff clean.
